# [2026.09.11 ~ 09.18 주간 질문 정리 — 내가 이번 주에 뭘 알고 싶었나]

## 한 줄 정의
- (이번 주 내가 GPT에 던진 질문들은 "LLM을 내 손으로 골라서 실험하고, 그걸 서버에 올려서 남이 쓰게 만들고, 그 전체 과정을 AI 에이전트에게 위임하는 법"을 알아내려는 하나의 흐름이었다)

## 왜 필요한가 / 어떤 문제를 해결하는가
1. 지금까지는 "모델 내부 구조(Attention, Transformer)"를 이해하는 단계였는데, 이번 주는 그 모델을 **실제로 고르고(모델 선정) → 같은 조건에서 실험하고(평가) → 서비스로 배포하고(AWS/DB) → 개발 자체를 에이전트에 맡기는(Claude Code/MCP)** 단계로 관심이 이동했다.
2. 질문의 절반 이상이 "이게 왜 그 위치에 있는가"였다. 즉 개별 기술 암기가 아니라 **기술 간의 관계도(지식 그래프)** 를 만들려는 목적이 계속 깔려 있었다.
3. 나머지 절반은 내 아이디어(논문 → 가상 실험실, 외신 기사 분류 LLM)를 **실현 가능한 아키텍처로 내려앉히는 작업**이었다. "시중에 있나 / 실용성 판단해줘 / 초안 써줘" 같은 질문이 반복됨.
4. 그래서 이번 주는 "공부 주제"가 아니라 **하나의 프로젝트 파이프라인을 세우는 주**였다고 보는 게 맞다.

```text
  ⑥ 운영 & 비용
     API 예산·호출 한도 설정, 토큰 사용량, 로컬 vs 클라우드 비용 비교
```

## 핵심 키워드

1. 모델 선정 — 요구사항(한국어/노트북 실행/라이선스)을 먼저 정하고 후보 2개를 같은 조건에서 비교한다.
2. 로컬 LLM vs Cloud LLM — 내 PC(Ollama)에서 돌리는지, 남의 서버를 API로 부르는지의 차이.
3. 양자화(GGUF, Q4_K_M) — 모델을 작게 만들어 로컬에서 돌아가게 하는 방식.
4. GQA (Q 28 / KV 4) — KV head를 줄여 메모리·속도를 절약하는 Attention 구조.
5. 컨텍스트 길이(32K/256K) — 한 번에 볼 수 있는 입력 길이.
6. 평가 지표 — Accuracy / Precision / Recall / F1 + 형식 준수율 + valid_calls.
7. valid_calls — 호출 성공(call_success)과 다르다. 채점 규칙을 통과한 "유효 응답"의 수.
8. temperature — 확률 분포를 날카롭게/부드럽게 만드는 값. 모델에 따라 기본값(1)만 허용돼 400 에러가 난다.
9. Tool Calling — 사용자 입력 → LLM이 도구 선택 → arguments 생성 → 함수 실행 → 결과 반환 → 최종 답변.
10. Agent Loop / Sub-Agent — 멀티에이전트는 새로운 개념이 아니라 이 루프를 나누고 겹친 구조.
11. Plugin / MCP / Skill / Tool — Plugin=기능 묶음, MCP=외부 연결 표준, Skill=작업 매뉴얼, Tool=실제 호출 가능한 기능.
12. ADE(Orca / Superset / Emdash / Conductor) — 코딩 에이전트를 여러 개 병렬로 굴리는 관리 환경.
13. Hermes / Aside — Hermes=스스로 장시간 일하는 자율 Agent, Aside=로그인된 브라우저를 직접 조작하는 업무 Agent.
14. PR / merge / fetch / Behind-Ahead — 내 코드를 남의 메인 브랜치에 안전하게 합치는 절차와 상태 표시.
15. .gitignore / .env — API 키 같은 비밀값은 파일로 관리하고 Git에는 절대 올리지 않는다.
16. CI/CD — push하면 자동 테스트·빌드·배포까지 이어지는 자동화.
17. EC2 / S3 / RDS / IAM / AMI — 서버 / 정적파일 / DB / 권한 / 이미지(리전별로 다름).
18. FastAPI / Vercel — 파이썬 백엔드 서버 프레임워크 / 프론트 배포 플랫폼. 보통 따로 올린다.
19. 고정IP(Static) / DHCP / TCP — 서버 주소를 고정하는 이유와 자동 할당·연결 보장 방식.
20. Interactive Virtual Lab — 논문을 넣으면 그 논문의 실험실이 화면에 차려지고, 사용자↔AI↔실험이 상호작용하는 내 아이디어의 핵심.

# [모델 선정과 비교 실험]이 내부적으로 동작하는 방식

## 궁금했던 질문
- 로컬 모델이라는 게 허깅페이스에서 골라서 올라마에 올려야 되는 건가?
- Cloud 모델이 정확히 뭐야? 서버 보내서 API로 쓰는 모델 말하는 거지?
- 한 분류 데이터셋을 두 모델로 돌려서 다르게 분류한 부분을 비교할 수 있나? 모델을 뜯어볼 수도 없는데?
- 이걸 비교해주는 평가지표가 있나?
- Qwen은 어떤 버전이 분류 모델에 좋을까? Qwen3-4B랑 클라우드 LLM 수준은 많이 차이나?
- 5.5조 토큰 학습, GGUF 양자화, GQA(Q 28 / KV 4), 32K 컨텍스트가 각각 무슨 뜻이야?
- Qwen vs CodeLlama vs DeepSeek-Coder, 세 모델의 주 학습 언어와 데이터셋을 알 수 있나?
- valid_calls = 0인데 call_success = 2인 건 뭐야? 호출이 실패한 거야?
- temperature가 정확히 뭘 하는 거고, 언제 높게/낮게 설정해?

## 찾아본 내용 요약
- 로컬 모델은 **Hugging Face에서 후보 조사 → Ollama에서 실행 가능한 태그 확인 → `ollama pull` → Python으로 호출** 순서. 굳이 내가 변환해서 올릴 필요는 없다.
- Cloud 모델은 내 PC가 아니라 **제공사 서버에서 실행되고 API로 호출**하는 방식. 로컬은 보안·무료, 클라우드는 품질·속도 우위.
- 두 모델 비교는 내부를 뜯는 게 아니라 **완전히 같은 입력·같은 프롬프트를 넣고 출력과 오류 패턴을 비교**하면 된다. ① 둘 다 정답 ② A만 정답 ③ B만 정답 ④ 둘 다 오답으로 쪼개면 차이가 보인다.
- 평가지표는 LLM용 특별한 게 필요 없고 **Accuracy / Precision / Recall / F1 / Confusion Matrix** 로 충분. 여기에 형식 준수율, 응답 속도(tok/s), VRAM을 붙이면 실험 보고서가 된다.
- 분류 과제에는 **Qwen3-4B-Instruct-2507-Q4_K_M** 이 1순위. 지시문 이해력이 괜찮으면서 4B라 로컬 부담이 적고, Q4_K_M 양자화로 약 2.5GB, 컨텍스트가 넉넉하다.
- 실제로 돌린 뉴스 제목 10개 분류 실험 결과는 **6/10 (60%)** 였고, 오답은 IT과학↔경제처럼 경계가 애매한 카테고리에서 났다. 모델에게 `Q01: 스포츠` 같은 **고정 출력 형식**을 지시해야 파싱이 안정된다.
- 용어 정리: **토큰 5.5조 = 학습량**, **GGUF = 로컬 실행용 저장/양자화 포맷**, **GQA = KV head를 줄여 메모리 절약(Q 28개가 KV 4개를 공유)**, **32K 컨텍스트 = 한 번에 읽을 수 있는 길이**.
- 코드 모델 비교에서 Qwen2.5-Coder-7B는 같은 7B·같은 Q4 양자화의 CodeLlama-7B / DeepSeek-Coder-6.7B와 하드웨어 프로파일은 거의 같은데 **형식 준수와 실제 정답률에서 앞섰다**. 학습 데이터 공개 수준은 DeepSeek > Qwen > CodeLlama 순으로 투명하다.
- `valid_calls = 0`은 호출 실패가 아니라 **호출은 성공했지만 채점 규칙이 "유효"로 인정한 응답이 0건**이라는 뜻. call_success와 valid_calls를 분리해서 봐야 한다.
- temperature는 확률 분포를 날카롭게(낮음) / 부드럽게(높음) 만드는 값. 분류·추출처럼 정답이 하나면 낮게, 아이디어·문장 생성이면 높게. 단 모델에 따라 **기본값 1만 지원**해서 0.2를 넣으면 `400 invalid_request_error`가 난다(이번 주 실제로 겪음).

## 결론
- 이번 주 모델 관련 질문의 진짜 목적은 "어떤 모델이 좋냐"가 아니라 **동일 조건 실험 → 수치 → 선정 근거**라는 실험 설계 자체를 손에 익히는 것이었다.

# [배포 · 인프라 · DB]가 내부적으로 동작하는 방식

## 궁금했던 질문
- AWS가 정확히 뭐고 왜 쓰는 거야? IAM으로 로그인하는 방법?
- AMI ID가 유효하지 않다는데 왜 이러지? 권한이 없다는 메시지는 뭐야?
- HTML 만들어서 AWS에 올리려면 어떻게 해?
- EC2로 인스턴스 만드는 것까지 배웠는데, Cloud API 쓴 프로그램을 사용자들이 쓰게 하려면 전체 과정이 어떻게 돼?
- 백엔드랑 프론트엔드를 따로 올려? FastAPI는 프로그램만 올리는 거고 DB는 따로 RDS에 올려야 되는 거 아냐?
- Vercel이 뭐고, EC2랑 Vercel은 어떤 기준으로 갈려?
- DBeaver에서 MySQL 연동하는 방법 / Public Key Retrieval is not allowed / Unknown database 'practice'
- 로컬로 연습한 MySQL을 AWS로 옮길 수 있어? 개발자들도 로컬에서 만들고 옮겨?
- DBMS랑 static이 비교 대상 맞아? DHCP는 뭐고 TCP는 뭐야?
- 도커는 배포할 때만 쓰면 되지? 프로젝트할 때는 필요 없잖아?

## 찾아본 내용 요약
- AWS 계정 구조는 **Root(주인) → IAM 사용자(권한 받은 계정)**. AMI 오류의 1순위 원인은 **리전 불일치**(AMI는 리전별로 존재), 2순위는 IAM 권한 부족. 그래서 `계정 종류 확인 → 권한 확인 → 리전 확인` 순서로 잡는다.
- 정적 HTML/CSS/JS만 있으면 EC2가 아니라 **S3 정적 호스팅**이 제일 쉽다. (실제로 다크 테마 HTML 자기소개서 만들어서 이 경로로 정리)
- 서비스 전체 배포 흐름:
  ```text
  사용자 → Frontend(Vercel) → Backend FastAPI(EC2, uvicorn :8000) → DB(RDS/MySQL)
                                             └→ 외부 LLM API(OpenAI 등)
  ```
  프론트와 백엔드는 **보통 따로 배포**한다. FastAPI는 요청을 받아 AI/DB/파일 처리를 중계하는 서버이고, DB는 FastAPI 안에 들어가는 게 아니라 **RDS 같은 별도 위치**에 둔다.
- EC2 vs Vercel의 기준은 "사이트가 복잡한가"가 아니라 **서버를 얼마나 직접 제어해야 하는가**. 포트폴리오·React는 Vercel, 상시 실행되는 파이썬 서버·모델 추론은 EC2.
- DBeaver + MySQL 트러블슈팅: JDBC 드라이버는 Download 버튼으로 자동 설치, `Public Key Retrieval is not allowed`는 **Driver properties → allowPublicKeyRetrieval = true**, `Unknown database`는 `CREATE DATABASE` 먼저 단독 실행 후 `USE`, 좌측 트리에 안 보이면 **F5 / Refresh**.
- 로컬 MySQL → AWS 이전은 흔한 작업. **`.sql` 덤프 백업 → RDS에서 복원**. 현업도 로컬에서 만들고 옮기는 방식이 일반적.
- DBMS와 static은 비교 대상이 아니다. DBMS는 데이터 관리 소프트웨어, static/dynamic은 **IP 할당 방식**. 서버는 주소가 바뀌면 안 되니까 고정IP, 일반 사용자 기기는 수가 많아 **DHCP가 lease time 단위로 자동 할당**. TCP는 그 위에서 **데이터가 순서대로 빠짐없이 도착하도록 보장**하는 규약.
- Docker는 "배포 전용"이 아니지만 **혼자 하는 초기 프로젝트에서는 굳이 필요 없다**. 팀 협업·환경 재현·서버 배포 단계에서 가치가 생긴다.

## 결론
- 배포 질문들은 결국 하나의 그림으로 합쳐졌다: **내 코드 → Git → 자동 빌드 → 서버(EC2) → DB(RDS) → 사용자(Vercel/도메인)**. 각 도구는 이 흐름 안의 위치로 기억하면 된다.

# [Git 협업 흐름]이 내부적으로 동작하는 방식

## 궁금했던 질문
- PR이 뭐야 풀리퀘스트야? merge는 뭐야? 그냥 실행하면 되지 왜 요청을 하지?
- PR하면 메인에 문제가 생기나?
- merge는 어떻게 합치는 거지? 그냥 폴더만 들고 오는 건가? 충돌 안 일어나?
- git fetch는 뭐하는 친구야? GitHub의 Behind / Ahead는 무슨 뜻이야?
- 공개 repository에서 가져와서 내가 파인튜닝한 다음 PR해도 되나?
- 전혀 일면식 없는 내가 만든 PR을 만든 사람이 가져가서 쓸 수도 있는 거네?
- .gitignore이 뭐고 그 안에 .env가 있는 건 왜야? API 키를 .env에 넣으면 되는 거 아냐?

## 찾아본 내용 요약
- 현업 흐름: **clone → 브랜치 생성(feature/xxx) → 작업 → commit → push → PR → 코드 리뷰 → merge → 배포**. PR은 "내 변경을 메인에 합쳐도 되냐"는 **검토 요청**이라서, PR 자체로는 메인이 바뀌지 않는다.
- merge는 폴더 복사가 아니라 **커밋 이력을 비교해서 변경을 합치는 것**. 같은 파일의 같은 줄을 서로 다르게 고쳤을 때만 충돌이 나고, 그럴 땐 사람이 직접 선택한다.
- `git fetch`는 **원격의 최신 정보만 가져오고 내 작업 파일은 건드리지 않는다**. Behind/Ahead는 내 브랜치가 원격보다 커밋 몇 개 앞/뒤인지 표시.
- 오픈소스 기여 경로: **Fork → 내 저장소에서 수정 → PR → 관리자 리뷰 → Merge**. 모르는 사람의 PR도 관리자가 승인하면 반영된다. 단 라이선스와 기여 가이드는 확인 필요.
- `.gitignore`는 Git이 추적하지 않을 파일 목록. API 키는 `.env`에 넣는 게 맞지만 **그 `.env`를 반드시 .gitignore에 넣어 원격에 올리지 않는 것**이 핵심. 배포에서는 GitHub Secrets / 서버 환경변수로 주입한다.
- GitHub Actions는 항상 Docker를 실행하는 건 아니고, 보통 **push → 테스트 → Docker 이미지 빌드 → 레지스트리 push → 서버 배포** 흐름 중 필요한 단계만 자동화한다. CI = 자동 테스트/빌드, CD = 자동 배포.

## 결론
- Git 질문의 핵심은 명령어가 아니라 **"내 코드를 남의 메인에 안전하게 합치는 절차"** 였다. 비밀값 분리(.env + .gitignore)까지가 한 세트다.

# [내 아이디어: Interactive Virtual Research Lab]이 내부적으로 동작하는 방식

## 궁금했던 질문
- 논문을 넣으면 실제 환경에서 실행되는 것처럼 비전으로 실험 세팅이 되고, 내가 직접 실험해서 결과를 볼 수 있으면 좋겠다. 시중에 있나? 실용성을 세심히 판단해줘
- 이 과정에 AI를 적용한다는 게 어떤 도움이 될까?
- 예를 들어 DINO 논문을 공부하면 기존 비전 모델과 비교 실험이 필요한데, 지금은 직접 코드 치거나 남의 자료 보는 수밖에 없잖아. 그걸 해결하고 싶은 거야
- 시각화만 하면 안 되지. 이거의 중요성은 **사용자와 AI와 작업의 인터랙티브**야
- 논문을 읽으면서 컴퓨터 화면에 내 실험실을 차리는 거야
- ONNX Runtime Web은 어떻게 쓰는 거야?
- 사용자와 인터랙티브하게 작동하는 시뮬레이션 프로그램은 이미 없나?
- (별개 아이디어) 외국 기사를 읽고 분류해서 알려주는 LLM 시스템, 이점을 늘려서 2개만 뽑아봐
- 문서 분류가 필요한 실제 사업 사례 / 문서 불량 판별 사례 / 쓸 수 있는 불량품 데이터셋이 있나?

## 찾아본 내용 요약
- 조각 기술은 이미 많지만 **"논문 입력 → 실험 자동 구성 → 내가 조작 → 결과 관찰 → 변형 반복"을 한 번에 해주는 범용 제품은 아직 자리 잡지 않았다**는 결론. 즉 빈 자리가 있다.
- 아이디어의 중심축이 이번 주에 확정됐다. **시각화는 부가 기능이고, 핵심은 `사용자 ↔ AI ↔ 실험`의 인터랙션 루프**.
  ```text
  논문 입력
     ↓
  AI 연구자(논문 이해/실험 절차 추출)
     ↓
  실험 환경 자동 구성 (예: DINO Virtual Lab)
     ↓
  사용자가 직접 조작 (모델 교체 / 하이퍼파라미터 변경 / 입력 이미지 교체)
     ↓
  결과 비교 (DINO vs ViT vs SimCLR) + AI의 해설·질문
     ↓
  다시 논문으로 (읽으면서 실험, 실험하면서 읽기)
  ```
- AI의 역할은 자동화가 아니라 **논문과 시뮬레이션 사이의 통역사 + 실험 코치 + 연구 파트너**. "왜 이 결과가 나왔는지"를 되묻는 기능이 학습 가치의 핵심.
- 구현 후보 기술로 **ONNX Runtime Web**(브라우저에서 ONNX 모델 직접 추론, WASM/WebGPU/WebNN 선택)을 확인. 서버로 이미지를 보내지 않고 사용자 PC에서 돌리므로 초기 비용이 거의 없다.
- MVP 구조 조언: 거대한 멀티에이전트로 시작하지 말고 **단일 Research Agent + Tool Loop**로 만들고, MCP를 외부 자료 검색/저장 서버로 붙인 뒤, 검색·분석·비평을 Sub-Agent로 분리하며 확장.
- 외신 기사 아이디어는 "번역+분류"로 가면 흔해지고, **"이 기사가 나에게 필요한가"를 LLM이 판단(주제·중요도·난이도·한국 관련성)** 하는 쪽으로 틀어야 차별화된다.
- 문서 분류는 기업 적용 사례가 많다(법무 NDA/계약서, 금융 대출·소득증빙, 보험 사고접수·진단서 등). **문서 "불량" 판별**도 현실적 주제(견적서를 세금계산서로 제출, 훼손·누락 서류 등).
- 특정 기업 제품의 불량 데이터셋은 공개된 게 거의 없고, **MVTec LOCO AD, MMAD-GoodsAD(food_bottle)** 같은 공개 산업 이상탐지 데이터셋으로 대체하는 게 현실적.
- 공모전 방향은 "AI API 붙인 CRUD"로는 차별화가 안 되고, **실제 뉴스에 나온 사회문제를 골라 AI로 예방/조기발견/대응하는 구조**가 강하다(2026 행안부 AI 경진대회 주제도 고의교통사고·딥보이스 탐지·공공입찰 위반 탐지).

## 결론
- 이번 주에 아이디어가 "가상 실험실을 만든다"에서 **"논문을 읽는 순간 그 논문의 실험실이 차려지고, AI와 대화하면서 실험을 변형해보는 학습 환경"** 으로 정의가 좁혀졌다. 다음 할 일은 DINO 하나로 MVP 범위를 자르는 것.

# [LLM API와 Agent 코드 구조]가 내부적으로 동작하는 방식

## 궁금했던 질문
- `responses.create()` / `POST /responses` 이런 걸 알아서 뭐해? API 연동하면 다 똑같은 거 아냐? 목적마다 다른 API를 내가 찾아 맞춰야 되는 거야?
- 코덱스에 시키면 얘가 API 기능마다 찾아서 쓰는 거야? 서브에이전트마다 API가 다를 가능성이 높겠네?
- 이렇게 된 API를 어떻게 써? `...`도 키야?
- Function Calling 왕복 코드에서 각 부분이 아키텍처의 어디에 해당해?
- 멀티에이전트/서브에이전트는 에이전트 루프가 많아지거나 작아지는 개념이야? 내가 생각하는 AI 에이전트와 다른가?
- 저 코드 방식으로 논문 정리 시스템을 실제로 짜면 구조가 어떻게 되고 어떤 문서·파일·도구·스킬이 필요해?
- 8-1~8-3 파일 전체를 시험 대비용으로 빠짐없이 정리해줘 (강의: Attention/MHA shape, Tool Calling, 멀티모달, 구조화 출력, 견고성)

## 찾아본 내용 요약
- API 문서를 읽는 이유는 "엔드포인트 암기"가 아니라 **내가 무엇을 요청하고 무엇을 돌려받는지(입력 스키마/출력 스키마)를 아는 것**. 연동 방식은 비슷해도 목적별 파라미터가 다르다.
- Tool Calling 왕복 구조:
  ```text
  사용자 입력 → LLM 판단 → tool 선택 → arguments(JSON) 생성
            → 내 함수 실행 → 실행 결과를 다시 LLM에 전달 → 최종 자연어 답변
  ```
  이 루프를 `max_rounds`로 제한하는 게 실전 코드의 기본형.
- **멀티에이전트/서브에이전트는 새로운 개념이 아니라 이 Agent Loop를 어떻게 쪼개고 쌓느냐의 문제**. 내가 생각한 "여러 단계로 생각하고 실행하는 AI"가 이미 전형적인 Agent 구조였다.
- 역할 분리를 명확히 잡았다: **OpenAI API = 런타임 두뇌, MCP = 외부 도구 연결, Skills = 반복 작업 지침, Codex/Claude Code = 이 전체를 구현·수정하는 개발 에이전트**. Codex와 OpenAI API는 같은 층이 아니다.
- 논문 정리 시스템 아키텍처는 **MVP = 단일 Research Agent + Tool Loop**, 확장 시 검색/분석/비평 Sub-Agent 분리. 필요한 것은 저장소 구조, plan 문서, tool 정의(JSON schema), 결과 저장 포맷.
- 강의 정리 관점에서 8~10장은 따로가 아니라 하나의 발전 과정이다: **도구 사용(Tool/Function Calling) → 멀티모달 입력 → 구조화 출력 보장 → 실패에 견디는 견고성**.

## 결론
- API 질문의 결론은 "코드를 외우자"가 아니라 **Agent = LLM + Tool + Loop + 상태**라는 한 문장으로 수렴했다. 이 구조를 잡으면 코덱스에게 시킬 때도 요구를 정확히 말할 수 있다.

- 인터넷 속도 26Mbps인데 괜찮은 거야?

## 찾아본 내용 요약
- 빛은 진공에서 멈출 수 없고, **공중의 특정 지점에 고정된 발광점을 만들기 어려운 것**이 공중 홀로그램의 본질적 난점. 플라즈마는 모양을 어느 정도 제어할 수 있지만 3D 형상을 유지하는 매질이 아니다. 아이언맨식 기능은 항목별로 쪼개면 AR/light-field/volumetric display로 일부만 실현 가능.
- 형광·인광·업컨버전(낮은 에너지 빛 여러 개 → 높은 에너지 빛 하나) 물질이 발광점 후보이고, **파장을 바꾸면 상호작용 물질이 늘지만 에너지가 높다고 유리하지는 않다**(안전·효율 문제).
- 공간 구조 파악은 **LiDAR / ToF / 3D LiDAR SLAM** 계열이고, 사람 검출·자세 추적까지 가능하다(포인트 클라우드 수준).
- 리눅스: `compgen -c`(명령어 전체), **`fork()` → `exec()` → `wait()` 한 세트**, `ps -o ppid=` / `echo $$ $PPID`, `pstree`, `clear`(Ctrl+L).
- 학습 로드맵 조사 결과, MIT 커리큘럼 자체가 **프로그래밍 → 수학 → 데이터/모델 → 의사결정 → 시스템 → 로보틱스/NLP/하드웨어**로 연결돼 있어서 내가 말한 "지식 관계도" 접근이 실제 상위권 교육과 맞닿아 있었다. 추천 포지션은 **Agentic AI × ML Systems × Embodied/Physical AI를 연결하는 시스템 빌더**.
- 가장 필요한 능력은 지식량이 아니라 **문제를 구조화하고 필요한 지식을 스스로 연결해 해결하는 능력**. AI가 발전할수록 지식 자체의 희소성은 떨어진다.
- 주식은 주식 수가 사라지는 게 아니라 **평가금액이 변하는 것**이고(1주는 그대로), 현물은 투자금 이상으로 마이너스가 나지 않는다(레버리지·파생은 다름).
- 인터넷은 26/24Mbps로 기본 속도는 보통이지만 **부하 시 지연이 37ms → 291ms로 급증**(버퍼블로트 경향). 실시간 작업·화상보다 다운로드형 작업에 유리.

## 결론
- 곁길처럼 보이지만 결국 **"3D 공간·센서 데이터·비전"** 이라는 같은 방향이었다. 홀로그램/LiDAR 호기심은 Interactive Lab의 시각·공간 파트와 연결된다.
