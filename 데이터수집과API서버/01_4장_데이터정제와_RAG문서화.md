# 4장. 데이터 정제와 RAG 문서화

## 핵심 키워드 10개

1. **결측치**: 키가 없거나 `None`, 빈 문자열, 공백만 있는 값처럼 실제로 사용할 내용이 없는 상태
2. **중복**: 같은 문서를 뜻하는 안정적인 식별자(여기서는 `source_id`)가 반복된 상태
3. **원천 데이터 보존**: 정제 전 JSON을 덮어쓰지 않고 별도 결과를 만드는 원칙
4. **텍스트 정규화**: HTML entity·태그·연속 공백을 읽기 쉬운 일반 텍스트로 통일하는 작업
5. **날짜 표준화**: 여러 날짜 입력을 `YYYY-MM-DD`로 맞추는 작업
6. **재현성**: 같은 입력과 규칙으로 실행할 때 같은 결과와 순서가 나오는 성질
7. **content**: 사용자의 질문과 의미적으로 비교할 검색 본문
8. **metadata**: 제목·URL·게시일처럼 표시, 필터, 출처 확인에 쓰는 부가 정보
9. **document_id**: 문서를 안정적으로 다시 찾기 위한 고유 ID
10. **문서 계약**: RAG에 저장할 문서의 필수 필드와 구조를 미리 정한 약속

## 핵심 내용 정리

### 4-1. 데이터 정제

- JSON 파일을 읽을 수 있다고 바로 활용 가능한 데이터가 되는 것은 아닙니다. 제목의 공백, HTML 본문, 제각각인 날짜 형식처럼 검색과 화면 표시에 문제를 주는 값을 먼저 정리합니다.
- 결측치는 키가 없는 경우에만 생기지 않습니다. `None`, `""`, `"   "`도 필수 문자열이 없다는 뜻이므로 `not value.strip()`처럼 공백을 제거한 뒤 판단합니다.
- 중복 여부는 제목이 아니라 원천의 안정적인 ID인 `source_id`로 판단합니다. `set`에 이미 처리한 ID를 저장해 두면 중복을 쉽게 걸러낼 수 있습니다.
- HTML 처리 순서는 **entity 해제 → 태그 제거 → 공백 통일**입니다. 예를 들어 `&nbsp;`를 문자로 되돌리고, `<p>`를 제거한 뒤 `" ".join(text.split())`으로 공백·탭·줄바꿈을 한 칸으로 맞춥니다.
- 날짜는 허용한 입력 형식만 차례로 파싱하여 `YYYY-MM-DD`로 바꿉니다. 읽을 수 없는 날짜를 오늘 날짜나 추측한 날짜로 바꾸면 사실성과 재현성이 깨집니다.
- 처리 결과에는 입력·정상·중복·제외 건수를 기록합니다. 항상 `입력 = 정상 + 중복 + 제외`가 맞는지 확인하면 누락된 분기를 발견하기 쉽습니다.

### 4-2. RAG 문서셋 만들기

- 정제 레코드는 수집 관점의 구조입니다. 이를 RAG에 쓰기 좋게 `document_id`, `content`, `metadata` 구조로 변환합니다.
- `content`에는 질문과 직접 비교할 본문(`body_text`)을 둡니다. URL, 날짜, ID를 본문에 반복해서 넣으면 의미 검색의 품질이 떨어질 수 있습니다.
- `metadata`에는 `title`, `source_url`, `published_at`, `source_id`처럼 결과 표시, 날짜 필터, 원문 확인에 필요한 정보를 둡니다.
- `document_id`는 바뀔 수 있고 중복될 수 있는 제목보다 원천 `source_id`를 바탕으로 만듭니다. 같은 원천 ID는 항상 같은 문서 ID가 되도록 안전한 문자만 남기고 접두사를 붙입니다.
- 변환 뒤에는 필수값, 문서 ID의 중복, JSON 배열의 순서를 검증한 뒤 UTF-8 `documents.json`으로 저장합니다. 저장한 파일을 다시 읽어 구조와 내용이 같은지도 확인합니다.

## 헷갈리기 쉬운 부분

| 구분 | 정확한 이해 |
| --- | --- |
| 결측치 vs 빈 값 | 키가 없어야만 결측치가 아닙니다. 공백만 있는 필수 문자열도 사용할 수 없는 결측입니다. |
| 중복 vs 같은 제목 | 같은 제목의 서로 다른 기사가 있을 수 있습니다. 가능한 한 `source_id` 같은 원천 ID를 기준으로 판단합니다. |
| HTML 태그 vs entity | `<p>`는 태그이고 `&nbsp;`는 entity입니다. 둘은 다른 방식으로 처리합니다. |
| 날짜 표준화 vs 날짜 추측 | 형식 변환은 원래 날짜를 보존하지만, 실패값을 오늘 날짜로 채우는 것은 새 사실을 만드는 일입니다. |
| content vs metadata | 의미 검색 대상은 `content`, 필터·표시·출처 정보는 `metadata`입니다. |
| document_id vs 내용 버전 | ID는 문서를 식별하고, 내용 버전은 문서가 변경됐는지를 나타냅니다. 같은 개념이 아닙니다. |

## 실전에 많이 쓰는 부분

- **수집 파이프라인**: 외부 API·크롤러 데이터는 원본을 보존하고, 정제 결과와 제외 사유·건수를 별도로 남깁니다.
- **중복 방지**: 뉴스, 상품, 고객 데이터 적재 시 제공처 ID나 URL 정규화 값을 기준으로 중복 삽입을 막습니다.
- **검색 품질 개선**: HTML과 불필요한 공백을 제거한 본문을 임베딩·키워드 검색에 사용합니다.
- **필터 가능한 RAG**: `published_at`, 출처, 태그를 metadata에 두어 “이번 달 자료만”, “특정 출처만” 같은 조건을 구현합니다.
- **추적 가능성**: 검색 결과에 제목·원문 URL을 함께 반환해 사용자가 근거 문서를 확인하도록 만듭니다.
- **운영 점검**: 입력 건수와 분류 건수의 합계, 고정된 문서 ID, 저장 파일 재읽기 검증을 자동화합니다.

## 한 줄 복습
