# 데이터 수집과 API 서버

## 1장 — 수집 방식 선택과 이용 가능성 확인

### 핵심 키워드 10개

| 키워드 | 간단한 설명 |
|---|---|
| 대표 질문 | 서비스가 실제로 답해야 하는 질문. 데이터 수집 방식은 이 질문에서 출발한다. |
| 수집 경로 | 데이터를 어디서 어떤 방법으로 받는지. 예: API, 파일 다운로드, 웹 수집 |
| 데이터 형식 | 데이터가 표현된 구조. 예: CSV, JSON, HTML, PDF |
| 질문 시점 API | 사용자가 질문한 순간 최신 데이터를 API로 조회하는 방식 |
| RAG | 관련 문서를 찾아 AI에게 함께 제공해 근거 있는 답변을 만들게 하는 방식 |
| 스냅샷 | 특정 시점의 API 응답이나 데이터를 파일로 저장한 기록 |
| 이용약관 | 자동 수집, 저장, 가공, 재배포 등을 다루는 서비스 사용 규칙 |
| robots.txt | 웹 크롤러가 접근해도 되는 경로를 안내하는 파일 |
| 개인정보 최소 수집 | 목적에 꼭 필요한 개인정보만 수집하고 불필요한 정보는 받지 않는 원칙 |
| 저작권·라이선스 | 콘텐츠를 복제·가공·공유할 수 있는 범위와 조건 |

### 핵심 내용

먼저 서비스가 답할 질문을 정한다.

| 질문 | 우선 검토 방식 | 이유 |
|---|---|---|
| "현재 대여 가능한 자전거 수는?" | 질문 시점 API | 지금 값이 중요해서 저장 문서가 낡을 수 있음 |
| "대여 규정과 예외는?" | 공식 문서 + RAG | 근거 문장과 앞뒤 문맥이 필요함 |
| "지난달 이용량 추이는?" | 파일 또는 주기적 스냅샷 | 과거 시점별 값을 비교해야 함 |

그다음 데이터를 가져오기 전, **기술적으로 가져올 수 있는가**와 **이용해도 되는가**를 분리한다.

- **이용약관/API 정책**: 자동 수집, 저장, 가공, 재배포 조건
- **robots.txt**: 웹 크롤러 접근 규칙
- **개인정보**: 꼭 필요한 정보만 수집하는지
- **저작권·라이선스**: 출처 표시, 가공, 상업 이용, 재배포 조건

### 퀘스트 수준 포인트

- API와 JSON은 같은 종류가 아니다.
  - API = 수집 경로
  - JSON = 데이터 형식
- 같은 API가 JSON 또는 CSV를 줄 수 있고, 다운로드 파일도 CSV 또는 JSON일 수 있다.
- robots.txt의 Allow는 "크롤러 접근 안내"일 뿐이다. 저작권 재배포 허락이나 약관 동의가 아니다.
- 이용 조건이 불명확하면 가능으로 넘기지 말고 **주의로 기록하고 멈춘다**.
- 개인정보 가능성이 있으면 자동 수집을 보류하고 **담당자 검토가 우선**이다.

### 헷갈리는 비교

| A | B | 핵심 차이 |
|---|---|---|
| 수집 경로 | 데이터 형식 | API/파일/웹 수집은 경로, CSV/JSON/PDF는 형식 |
| RAG | 질문 시점 API | RAG는 설명·규정용, API는 최신 수치용 |
| 정적 파일 | 스냅샷 | 정적 파일은 제공자가 배포, 스냅샷은 특정 시점 데이터를 직접 저장 |
| robots.txt | 저작권/라이선스 | 접근 규칙과 이용 권리는 별개 |
| 공개 페이지 | 자유 재사용 가능 자료 | 공개되어도 저장·가공·재배포는 제한될 수 있음 |
| checked_at | collected_at | 조건 확인일과 실제 데이터 수집 시각은 다름 |

## 2장 — HTTP 요청과 안전한 API 호출

### 핵심 키워드 10개

| 키워드 | 간단한 설명 |
|---|---|
| 클라이언트 | 데이터를 요청하는 프로그램. 예: Python으로 만든 수집 코드 |
| 서버 | 요청을 처리하고 결과를 돌려주는 프로그램 또는 시스템 |
| base URL | 여러 API 기능이 공통으로 쓰는 서버 주소와 기본 경로 |
| endpoint | 특정 기능이나 자원에 접근하는 세부 경로 |
| HTTP method | 서버에 요청하는 행동의 종류. 예: GET, POST |
| header | 인증 키, 응답 형식 등 요청의 부가 정보를 담는 영역 |
| query parameter | 검색어, 날짜, 페이지 번호처럼 조회 조건을 URL에 전달하는 값 |
| request body | 생성·수정할 데이터를 요청 본문에 담는 영역 |
| 상태 코드 | 요청 처리 결과를 나타내는 숫자. 예: 200, 401, 429 |
| raise_for_status() | 4xx·5xx 응답을 오류로 처리해 정상 데이터와 구분하는 함수 |

### 핵심 내용

API 호출은 **클라이언트가 서버에 요청하고 서버가 응답하는 흐름**이다.

요청 전 API 문서에서 꼭 확인할 항목은 여섯 가지다.
1. base URL
2. endpoint와 method
3. 인증 위치
4. 필수 parameter
5. 성공 응답 구조
6. 오류 코드와 호출 제한

안전한 호출 순서는 다음이다.
```text
환경 변수에서 API 키 읽기
   ↓
headers와 params 만들기
   ↓
timeout을 둔 요청
   ↓
상태 코드 확인
   ↓
JSON 파싱
   ↓
필요한 배열·필드의 자료형 확인
```

### 퀘스트 수준 포인트

- API 키는 코드에 직접 적지 않고 환경 변수에서 읽는다.
- params는 검색어, 날짜, 페이지 번호 같은 조회 조건이다.
- headers는 API 키, 인증 방식, 원하는 응답 형식 같은 부가 정보다.
- `response.json()`보다 `raise_for_status()`를 먼저 실행한다.
  - 오류 응답도 JSON일 수 있기 때문이다.
- 200이어도 items가 반드시 존재한다고 단정하면 안 된다. 배열인지 확인해야 한다.
- timeout은 요청이 무기한 멈추는 것을 막기 위한 기본 안전장치다.

### 상태 코드 빠른 정리

| 코드 | 뜻 | 먼저 할 일 |
|---|---|---|
| 200 | 성공 | 본문 구조·데이터 확인 |
| 400 | 요청 오류 | parameter 이름·값·자료형 확인 |
| 401 | 인증 실패 | API 키와 전달 위치 확인 |
| 403 | 권한 또는 정책상 거부 | 권한·이용 정책 확인 |
| 404 | 경로 또는 자원 없음 | endpoint·ID 확인 |
| 429 | 호출 과다 | 안내에 따라 대기 후 재시도 |
| 500 | 서버 내부 오류 | 요청 정보와 제공자 상태 확인 |

### 헷갈리는 비교

| A | B | 핵심 차이 |
|---|---|---|
| URL | endpoint | URL은 전체 주소, endpoint는 특정 기능 경로 |
| GET | POST | GET은 주로 조회, POST는 생성·작업 요청 |
| header | query parameter | header는 인증·형식, query는 검색·필터 조건 |
| query | body | query는 URL 조건, body는 서버에 보낼 데이터 |
| 401 | 403 | 401은 인증 실패, 403은 인증 여부와 별개로 권한/정책상 거부 |
| JSON 파싱 성공 | API 호출 성공 | 오류 응답도 JSON일 수 있으므로 상태 코드가 먼저 |

## 3장 — 페이지네이션, 429 재시도, 원본 보존

### 핵심 키워드 10개

| 키워드 | 간단한 설명 |
|---|---|
| 페이지네이션 | 많은 결과를 여러 페이지로 나누어 API가 반환하는 방식 |
| page | 요청할 데이터 묶음의 번호 |
| page_size | 한 페이지에서 받을 최대 항목 수 |
| has_next | 다음 페이지가 남아 있는지 알려 주는 값. False면 종료 |
| total_pages | 전체 페이지 수. 현재 페이지와 같으면 마지막 페이지 |
| extend() | 페이지 안의 여러 항목을 전체 리스트에 하나씩 이어 붙이는 함수 |
| 429 Too Many Requests | 짧은 시간에 요청을 너무 많이 보내 호출 제한에 걸린 상태 |
| raw_response.json | API가 돌려준 전체 원본 응답을 보관하는 파일 |
| items.json / items.csv | 필요한 필드만 추출해 분석이나 표 작업에 쓰기 좋게 만든 파일 |
| collection_log.json | 수집 시각, 출처, 건수, 성공 여부를 기록하는 로그 파일 |

### 핵심 내용

한 번에 너무 많은 데이터를 보내지 않기 위해 API는 결과를 여러 페이지로 나눈다.

반복 수집의 원칙:
1. page = 1부터 시작
2. 현재 페이지 요청
3. 성공하면 items를 전체 목록에 합침
4. 마지막 페이지인지 확인
5. 마지막이 아니면 page를 1 증가
6. 반복

**페이지 번호는 성공한 뒤에만 올린다.**

### 퀘스트 수준 포인트: 429

429는 요청을 너무 많이 보냈다는 뜻이다. 처리 순서:
```text
429 수신
   ↓
Retry-After 또는 API 문서의 대기 시간 확인
   ↓
대기
   ↓
page 번호는 유지
   ↓
같은 page 재요청
```

예를 들어 2페이지에서 429가 왔는데 3페이지로 넘어가면, 2페이지 데이터가 통째로 누락된다. 그래서 **"대기 후 같은 페이지를 재요청"**해야 한다.

### append()와 extend() 비교

```python
collected.extend(page_items)
```

- `extend()`는 페이지 안의 항목을 하나씩 전체 목록 뒤에 붙인다.
- `append(page_items)`는 페이지 목록 자체를 한 덩어리로 넣어 중첩 리스트를 만든다.

### 원본과 가공 파일을 분리하는 이유

| 파일 | 역할 |
|---|---|
| raw_response.json | API 응답 전체 원본 보관 |
| items.json | 필요한 필드만 추출한 분석용 데이터 |
| items.csv | 엑셀 등 표 도구용 데이터 |
| collection_log.json | 수집 시각, 출처, 건수, 성공 여부 기록 |

`raw_response.json`을 남기는 이유:
- 필드 추출 실수를 나중에 확인할 수 있음
- 새 필드가 필요할 때 API를 다시 호출하지 않아도 됨
- API 응답 구조가 바뀌었는지 비교 가능
- 정제 전 데이터가 어떤 모습이었는지 설명 가능

즉, **items.json으로 원본을 덮어쓰면 안 된다.**

### 저장 시 세부 포인트

- JSON: `ensure_ascii=False`로 한글을 읽기 좋게 저장
- CSV: `csv.DictWriter`로 쉼표·따옴표·줄바꿈 처리
- CSV 열 순서: `fieldnames`로 명시
- 로그에 남길 것: 출처, 수집 시각, 건수, 성공 상태
- 로그에 남기면 안 될 것: API 키, 인증 헤더, 개인정보가 담긴 응답 전체

### 헷갈리는 비교

| A | B | 핵심 차이 |
|---|---|---|
| page | page_size | 페이지 번호 vs 한 페이지 최대 항목 수 |
| has_next=False | 빈 items | 둘 다 종료 신호일 수 있지만, 어떤 규칙을 쓸지는 API 문서 기준 |
| 429 | 401 | 429는 호출 과다, 401은 인증 실패 |
| append() | extend() | 리스트 덩어리 추가 vs 항목별 추가 |
| raw_response.json | items.json | 원본 전체 보관 vs 필요한 필드만 추출 |
| collected_at | 데이터 관측 시각 | 응답을 받은 시각 vs 데이터 자체가 만들어진 시각 |

### 시험용 한 줄 정리

> 성공한 페이지의 항목을 `extend()`로 합친 뒤에만 다음 페이지로 넘어가고, 429에서는 기다린 후 같은 페이지를 재요청한다. 원본 응답은 별도 파일로 보존한다.
